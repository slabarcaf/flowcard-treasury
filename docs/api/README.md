# FlowCard Onboarding OpenAPI 3.1.0 Documentation

This directory contains the machine-readable OpenAPI 3.1.0 specifications and documentation architecture for the FlowCard company-onboarding subsystem.

## Architecture & Audience Separation

The onboarding subsystem separates its API surface into two audience-specific specifications:

1. **Operator API (`openapi.json`)**
   - **Audience**: Platform operators, internal administrative frontends (Kit 5), and trusted internal backend services.
   - **Operations**: 21 endpoints covering company records, onboarding applications, submission lifecycles, KYC document metadata and uploads, and connected platform accounts.
   - **Security Schemes**:
     - `GatewaySessionCookie`: Cookie-based session (`kit5_operator_session`) verified at the Node.js gateway proxy.
     - `ServiceJWT`: Signed short-lived HS256 JWT assertion (`Issuer: flowcard-node-proxy`, `Audience: flowcard-onboarding-service`) generated by the gateway for authenticated operator requests.

2. **Internal Webhook Receiver API (`webhooks.json`)**
   - **Audience**: Automated platform webhook ingress forwarders (Airwallex webhook processors).
   - **Operations**: 2 endpoints (`POST /api/webhooks/airwallex` and `POST /api/v1/webhooks/airwallex`).
   - **Security Scheme**:
     - `WebhookServiceJWT`: Signed short-lived HS256 JWT assertion (`Issuer: flowcard-node-proxy`, `Audience: flowcard-onboarding-webhooks`) emitted exclusively by the internal forwarder worker.

## Accessing the Documentation

### 1. Direct Go Service

When running the Go onboarding service directly (e.g. port 8080), documentation routes are served natively outside database and authentication gates:

- **Interactive Swagger UI**: `http://localhost:8080/docs/api` (redirects 301 to `http://localhost:8080/docs/api/`)
- **Operator API Spec**: `http://localhost:8080/docs/api/openapi.json`
- **Webhook API Spec**: `http://localhost:8080/docs/api/webhooks.json`

### 2. Node.js Gateway Proxy

When accessing through the FlowCard Node.js server (e.g. port 3000), documentation routes are proxied to the configured upstream service:

- **Interactive Swagger UI**: `http://localhost:3000/docs/api` (redirects 301 to `http://localhost:3000/docs/api/`)
- **Operator API Spec**: `http://localhost:3000/docs/api/openapi.json`
- **Webhook API Spec**: `http://localhost:3000/docs/api/webhooks.json`

> [!IMPORTANT]
> **Upstream Configuration & Gateway Defaults**
> The Node.js gateway documentation proxy requires an explicit `onboardingServiceUrl` in its server configuration. If `onboardingServiceUrl` is unset or empty, the gateway responds `503 Service Unavailable` with `{"error": "onboarding_service_unconfigured"}`. No fictitious environment variables are invented; configuration is injected via the existing server constructor.

## Security & Offline Properties

1. **Public & Read-Only**: Documentation endpoints (`/docs/api/*`) are public and unauthenticated. They require no database connection, no operator cookies, and no live credentials.
2. **Business API Protection**: Protected business endpoints (`/api/companies`, etc.) remain strictly authenticated. Unauthenticated requests to business APIs return `401 Unauthorized` (`operator_auth_required`).
3. **Credential Stripping**: The Node gateway strips incoming client `Cookie` and `Authorization` headers before proxying documentation requests upstream. No service JWT assertion is generated for docs requests.
4. **100% Offline & Isolated**: Swagger UI assets (`swagger-ui-dist@5.34.1`) are bundled directly inside the Go binary via `embed.FS`. The UI makes zero external network calls:
   - No Google Fonts or external typography
   - No external CDN scripts (cdnjs, unpkg)
   - Swagger validator disabled (`validatorUrl: null`)
   - Telemetry and analytics absent
   - Strict Content-Security-Policy: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; font-src 'self' data:; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`
5. **Read-Only Execution Controls**:
   - `supportedSubmitMethods: []` (Try-it-out disabled for all HTTP methods)
   - `tryItOutEnabled: false`
   - `persistAuthorization: false` (Zero credentials persisted to `localStorage` or `sessionStorage`)
   - `queryConfigEnabled: false` (Prevents remote `?configUrl=` or `?urls.primaryName=` injection)
6. **Method Filtering**: Mutating methods (`POST`, `PUT`, `DELETE`, `PATCH`) to documentation endpoints are immediately rejected with `405 Method Not Allowed` and `Allow: GET, HEAD`.

You can run and review the documentation locally without configuring PostgreSQL or external platform credentials:

```bash
# Start the Go service directly (runs with deny-by-default business endpoints, public docs active)
cd services/company-onboarding
PORT=8080 go run ./cmd/api -port 8080
```

Open `http://localhost:8080/docs/api/` in your browser:
- The offline Swagger UI loads immediately.
- Use the definition selector at the top to toggle between "Operator API" and "Internal Webhook Receiver API".
- All 23 business and webhook endpoints render with complete schemas, field constraints, status codes, and realistic examples.
- Business endpoints remain deny-by-default (unconfigured database returns 503).

## Specification Generation & Drift Prevention

### Artifact Locations & Mirrors

Specification files are generated from Go DTOs and operations metadata into two identical mirrors:
1. **Repository Documentation**:
   - `docs/api/openapi.json`
   - `docs/api/webhooks.json`
2. **Module Embedded Assets**:
   - `services/company-onboarding/internal/apidocs/specs/openapi.json`
   - `services/company-onboarding/internal/apidocs/specs/webhooks.json`

Both locations are kept byte-for-byte identical. Automated tests enforce that embedded mirrors never drift from repository artifacts.

### CLI Commands

The generator CLI is located at `services/company-onboarding/cmd/openapi`.

```bash
# Check specification freshness without modifying disk (ideal for CI)
# From repository root:
go -C services/company-onboarding run ./cmd/openapi -check

# Or from the Go module directory:
cd services/company-onboarding
go run ./cmd/openapi -check

# Regenerate specifications deterministically:
# From repository root:
go -C services/company-onboarding run ./cmd/openapi

# Or from the Go module directory:
cd services/company-onboarding
go run ./cmd/openapi
```

### Automated Drift Prevention

Automated tests in `services/company-onboarding/internal/apidocs/contracts_test.go` enforce continuous contract integrity:
1. **AST Route Parity**: Inspects `services/company-onboarding/internal/http/handlers.go` AST and validates a 1-to-1 bijection with `apidocs.AllOperations()`. Adding a route without documentation causes test failure.
2. **Negative Drift Checks**: Verifies that synthetic unapproved routes, undocumented webhooks, phantom operations, or corrupted/stale JSON on disk trigger test failures.
3. **Wire Schema Validation**: Validates actual emitted JSON payloads for raw arrays, request DTOs, gate 422 blocked errors, and auth error variants against OpenAPI 3.1 schemas.
4. **Credential Leak Scan**: Scans all emitted schemas and examples to guarantee zero tokens, passwords, private keys, or server JWT assertions.

## Adding Endpoints & Schema Customization Guide

When introducing a new API endpoint to the company-onboarding subsystem:

1. **Implement the HTTP Handler**: Add the route in `services/company-onboarding/internal/http/handlers.go` using standard Go 1.22+ pattern matching (e.g. `mux.HandleFunc("POST /api/companies", s.handleCreateCompany)`).
2. **Register Operation Metadata**: Add the corresponding `OperationDefinition` in `services/company-onboarding/internal/apidocs/operations.go` inside `AllOperations()`:
   - `ID`: Unique operation identifier (e.g. `createCompany`)
   - `Audience`: `"operator"` or `"internal-webhook"`
   - `Method` & `Path`: Exact HTTP method and route pattern matching `handlers.go`
   - `Summary` & `Description`: Human-readable purpose and contract nuances
   - `Tags`: Grouping category (e.g. `Companies`)
   - `Parameters`: Query, path, or header parameters
   - `RequestBody`: Request DTO reflection type or multipart definition
   - `Responses`: Map of HTTP status codes to response DTO types or raw array schemas
3. **Configure Schema Customization**: If the DTO requires custom schema behavior, update `SchemaCustomizer` in `services/company-onboarding/internal/apidocs/generate.go`:
   - Exclude internal fields using `json:"-"` and `openapi3gen.ExcludeSchemaSentinel`.
   - Apply scoped status enums (e.g. `CompanyResponse` status allows only `ACTIVE` or `ARCHIVED`).
   - Use native OpenAPI 3.1 null union types (`type: ["string", "null"]`).
4. **Regenerate & Verify**:
   ```bash
   go -C services/company-onboarding run ./cmd/openapi
   go test -v -race -count=1 ./services/company-onboarding/internal/apidocs/...
   ```

## Actual Implemented Contracts vs. Idealized Behaviors

The OpenAPI documentation reflects the exact runtime reality of the onboarding subsystem, including its active security boundaries and deferred gates:

1. **Blocked Application Submission Gate**:
   - `POST /api/onboarding-applications/{id}/submit` returns `422 Unprocessable Entity` with code `SUBMISSION_CONTRACT_BLOCKED`. Submission execution remains blocked pending explicit business resolution of the reviewed revisions policy.
2. **Scoped Status Enums**:
   - `CompanyResponse` status is strictly `ACTIVE` or `ARCHIVED` (initial status is `ACTIVE`; `DRAFT` is rejected as an invalid state).
   - `ApplicationResponse` has 7 discrete status values (`DRAFT`, `SUBMITTED`, `IN_REVIEW`, `APPROVED`, `REJECTED`, `CHANGES_REQUESTED`, `ERROR`).
   - `SubmissionResponse` has 4 discrete status values (`PENDING`, `ACCEPTED`, `FAILED`, `UNRESOLVED`).
   - `PlatformAccountResponse` status is documented as an open string reflecting external platform lifecycle values.
3. **Raw Array Responses**:
   - Platform account listings (`GET /api/companies/{id}/platform-accounts`), submission listings (`GET /api/onboarding-applications/{id}/submissions`), and document listings (`GET /api/onboarding-applications/{id}/documents`) return raw top-level JSON arrays (`[]`), not envelope objects.
4. **Authentication Error Disagreements**:
   - Gateway-rejected operator requests return `GatewayAuthError`: `{"error": "operator_auth_required"}`.
   - Go service-rejected requests return `ServiceAuthError`: `{"code": "UNAUTHORIZED", "message": "..."}`.
   - Both variants are documented under `401 Unauthorized` using an explicit `oneOf` discriminator schema.
5. **Deferred Onboarding Gates**:
   - Three pending implementation gates remain deferred in code and documented honestly:
     1. Revision review policy resolution (fail-closed submission contract).
     2. Document verification pipeline (returns 503 if S3 storage unconfigured).
     3. Platform contract readiness gate (blocks external account creation if Airwallex client unconfigured).
